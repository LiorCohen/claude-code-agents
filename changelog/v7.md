# Changelog - Version 7.x

All notable changes for major version 7 of the SDD plugin.

---

## [7.2.0] - 2026-02-23

### Changed

- **plugin architecture**: Split monolithic plugin into `core/` and `fullstack-typescript/` subdirectories
  - `plugin/core/` — Tech-agnostic SDD methodology (commands, orchestrators, lifecycle skills)
  - `plugin/fullstack-typescript/` — Concrete tech pack (Node.js, React, PostgreSQL, OpenAPI, Helm agents, skills, templates)
- **tech pack manifest**: New contract defines all integration points between core and tech packs (8 operations: readManifest, resolvePath, loadSkill, loadAgent, routeCommand, routeSkills, listComponents, dependencyOrder)
- **build system**: Dual build — `@sdd/core-system` and `@sdd/fs-ts-system` compile independently with separate tsconfigs
- **core skills**: Rewritten to discover tech pack content via manifest instead of hardcoded references
- **commands**: Made tech-agnostic — zero hardcoded tech pack names, component types, or tech-specific examples in core
- **settings**: Migrated project directory convention from `.sdd/` to `sdd/`

### Added

- **techpacks gateway skill**: Single entry point for all cross-boundary tech pack access
- **tech pack manifest schema**: JSON Schema validation for tech pack registration
- **agent frontmatter**: System commands for reading agent metadata without loading prompt bodies
- **logging commands**: Structured logging via system CLI for prompt-file diagnostics

### Rationale

Separating methodology from implementation enables reuse of the SDD lifecycle with different tech stacks. The tech pack manifest contract ensures core never hardcodes tech-specific content, making it possible to add new tech packs (e.g., Python/Django, Go/gRPC) without modifying core files. 435 files changed across 21 commits.

## [7.1.0] - 2026-02-18

### Added

- **workflow-state**: Add required `name` field to `WorkflowState` type — workflows now have user-chosen names (e.g., `user-auth`) instead of only opaque 6-char IDs
  - Directory layout changes from `.sdd/workflows/<id>/` to `.sdd/workflows/<id>-<name>/`
  - Change IDs derive from workflow name: `user-auth-1` instead of `a1b2-1`
  - Creation flow prompts user for workflow name (both interactive and external spec flows)
  - Backward compat: nameless workflow.yaml files derive name from first item title
- **workflow-state**: Add `workflow_id` parameter to `list()`, `get_current()`, `advance()`, `get_progress()`, `check_phase_gate()` operations (fixes single-workflow assumptions)
- **change-orchestration**: `list` action now handles multiple concurrent workflows
- **sdd command**: Change-id inference uses name prefix for direct workflow lookup

### Rationale

Workflows are the container for changes — they span multiple PRs, branches, and lifecycle phases. Without names, users see opaque `a1b2c3` IDs and have to inspect items to understand what a workflow is about. Name-based change IDs (`user-auth-1`) are instantly recognizable in listings, status displays, and branch names.

## [7.0.0] - 2026-02-16

### Changed

- **commands**: Collapse 6 user-facing commands into 3 with distinct personas:
  - `/sdd` — context-aware workflow hub ("Jarvis"), reads project state, accepts natural language
  - `/sdd-run` — thin dispatcher for direct namespaced operations (8 namespaces)
  - `/sdd-help` — read-only tutor for learning SDD concepts
- **sdd-run**: Rewrite as thin dispatcher routing to orchestrator skills (change, init, config, version, local-env) and pass-through namespaces (database, contract, permissions)
- **orchestrators**: Extract workflow logic from deleted commands into 5 orchestrator skill sets:
  - `change-orchestration/` — 7 files covering creation, spec-review, planning, implementation, verification, management
  - `init-orchestration/` — 6-phase project initialization
  - `config-orchestration/` — generate, validate, diff, add-env operations
  - `version-orchestration/` — version display with contextual output
  - `local-env-orchestration/` — 9 local k8s environment actions (moved from `skills/local-env/`)
- **database CLI**: Add `--env` flag support threading environment through all 7 database actions (setup, teardown, migrate, seed, reset, port-forward, psql)
- **references**: Update all old command references across 45 files:
  - Plugin skills: `/sdd-change X` → `/sdd I want to X` (natural language)
  - Agent files: `/sdd-run env` → `system-run.sh env` (direct CLI)
  - Marketplace skills: `/sdd-init` → `/sdd-run init` (namespaced)
  - Tests: rename 4 files, update 8 more with new command patterns
  - Docs: full rewrite of commands.md, updates to all 8 other doc files + README

### Added

- **sdd.md**: New Jarvis hub command with strict approval protocol, no-arg context reading, natural language routing
- **sdd-help.md**: New tutor command — read-only, no tools, progressive disclosure of SDD concepts
- **orchestrators/**: New skill directory with 5 orchestrator skill sets (11 total files)
- **plugin.json**: Add `./skills/orchestrators/` to skills array

### Removed

- **sdd-change.md**: Deleted (1144 lines → change-orchestration/)
- **sdd-config.md**: Deleted (270 lines → config-orchestration/)
- **sdd-init.md**: Deleted (307 lines → init-orchestration/)
- **sdd-settings.md**: Deleted (152 lines → project-settings skill)
- **sdd-version.md**: Deleted (87 lines → version-orchestration/)
- **skills/local-env/**: Deleted directory (moved to orchestrators/local-env-orchestration/)

### Rationale

Six commands with overlapping concerns created confusion about which command to use. The three-command structure provides clear entry points by experience level: `/sdd-help` for learning, `/sdd` for guided workflows, `/sdd-run` for direct operations. Orchestrator skills decouple workflow logic from the command surface, enabling future command changes without rewriting logic.
